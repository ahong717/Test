# RS232 調光器 Web 控制台開發筆記

**開發期間：** 2026/11/2～2026/11/3  
**整理依據：** 使用者提供的 DPI2、PD12V30W Modbus ASCII 協定圖、產品條件確認，以及目前 V1.1／S1.1 程式。  
**文件目的：** 保留產品差異、特殊通訊規則、03／06／10 指令格式、網頁現況、文字優化及驗證紀錄，供後續開發與實機測試追蹤。

---

## 一、開發重點摘要

本次工作的核心不是製作一般通用型 Modbus 工具，而是讓網頁依照廠商提供的產品協定圖產生與解析封包。

已確認的主要產品條件：

| 產品 | 解析度 | 網頁使用方式 | 重要提醒 |
|---|---:|---|---|
| DPI2 | 512 段 | 選擇「512 段」 | 數值範圍為 0～511，即 `0x0000～0x01FF` |
| PD12V30W | 256 段 | 選擇「256 段」 | 數值範圍為 0～255，即 `0x00～0xFF` |

兩種解析度不能只用一般 Modbus 習慣推測，必須依廠商協定處理。尤其功能碼 `10` 的多筆寫入資料寬度，在 256 段與 512 段模式下不同。

目前網頁已支援：

- 1、2、4、8 通道控制器。
- 256／512 段解析度切換。
- Modbus ASCII 功能碼 `03`、`06`、`10`。
- LRC 自動計算及接收驗證。
- `:` 起始字元及 `CR LF` 結尾。
- 任意有效的連續通道範圍，不強制從 CH1／暫存器 `0001` 開始。
- 03／06／10 回應解析與待回應請求比對。
- Web Serial 實體 COM Port 通訊。

## 二、協定共同基礎

### 2.1 傳輸格式

廠商規格使用 **Modbus ASCII only**。

完整封包共同形式：

```text
: + 站號 + 功能碼 + 指令資料 + LRC + CR + LF
```

| 欄位 | 長度 | 說明 |
|---|---:|---|
| Header | 1 字元 | 固定為 `:`，十六進位 ASCII 值為 `0x3A` |
| Additional address | 2 字元 | 站號，規格圖範例為 `01` |
| Function | 2 字元 | `03`、`06` 或 `10` |
| 指令資料 | 依功能碼變動 | 暫存器、數量、Byte Count、寫入資料等 |
| LRC | 2 字元 | 對站號至最後一個資料 Byte 計算 |
| Trailer | 2 個控制字元 | `CR LF`，十六進位為 `0D 0A` |

### 2.2 LRC 規則

LRC 計算不包含起始字元 `:`，也不包含結尾的 `CR LF`。

計算方式：

1. 將站號、功能碼及資料每兩個 HEX 字元視為一個 Byte。
2. 將所有 Byte 累加，只保留低 8 Bits。
3. 取二補數：`(0x100 - 總和) & 0xFF`。
4. 結果轉成兩位大寫 HEX。

例如：

```text
01 + 06 + 00 + 02 + 00 + 80 = 0x89
LRC = 0x100 - 0x89 = 0x77
```

所以完整 06 封包為：

```text
:01060002008077\r\n
```

### 2.3 `0x01AB` 與封包中的 `01AB`

`0x01AB` 與 `01AB` 是同一個十六進位數值，十進位為 427。

- `0x` 是畫面或文件用來表示「十六進位」的前綴。
- Modbus ASCII 封包只放 HEX 字元，因此線上封包使用 `01AB`，不能傳送字元 `x`。

## 三、功能碼 06：單筆寫入

### 3.1 PC 發送格式

```text
: + 站號(2) + 06 + 暫存器位址(4) + 暫存器數值(4) + LRC(2) + CRLF
```

規格圖範例：將 CH2／暫存器 `0002` 寫入 `0x0080`。

```text
:01060002008077\r\n
```

欄位拆解：

```text
: | 01 | 06 | 0002 | 0080 | 77 | CRLF
```

### 3.2 裝置回應格式

功能碼 06 的正常回應依規格圖原樣回送暫存器位址與寫入值：

```text
:01060002008077\r\n
```

### 3.3 256／512 段處理

- 06 的數值欄固定為 4 位 HEX。
- 256 段有效值：`0000～00FF`。
- 512 段有效值：`0000～01FF`。
- 網頁會依目前解析度阻止超過上限的數值。

### 3.4 目前網頁回應確認條件

只有下列資料全部相符，才顯示「06 寫入確認」：

- 回應 LRC 正確。
- 站號相符。
- 功能碼為 `06`。
- 暫存器位址與待回應請求相符。
- 回傳數值與送出數值相符。
- 回應來自實體 COM Port，而不是模擬資料。

## 四、功能碼 10：多筆連續寫入

### 4.1 PC 發送格式

```text
: + 站號(2) + 10 + 起始位址(4) + 數量(4)
  + Byte Count(2) + 多筆資料 + LRC(2) + CRLF
```

### 4.2 廠商特殊的 256／512 段資料寬度

這是本次最重要、也最容易被一般 Modbus 經驗誤判的規則。

| 模式 | 每通道寫入資料 | Qty = N 時資料長度 | Byte Count 欄位 |
|---|---:|---:|---:|
| 256 段 | 2 位 HEX／1 Byte | `N × 2` 位 HEX | 仍依規格圖填 `N × 2 Bytes` |
| 512 段 | 4 位 HEX／2 Bytes | `N × 4` 位 HEX | `N × 2 Bytes` |

一般標準 Modbus 會預期一個暫存器占 2 Bytes；但廠商提供的 256 段規格圖，在功能碼 10 的資料區使用每通道 2 位 HEX，同時 Byte Count 仍以 `Qty × 2` 填寫。這在一般邏輯上看似不一致，但屬於產品的特殊協定設計，網頁必須照規格圖產生，不能自行「修正」成另一種格式。

### 4.3 PD12V30W／256 段範例

從 CH1 開始寫入 4 通道，資料為 `10 20 30 40`：

```text
: | 01 | 10 | 0001 | 0004 | 08 | 10203040 | 42 | CRLF
```

完整封包：

```text
:011000010004081020304042\r\n
```

此處：

- 起始位址：`0001`
- Qty：`0004`
- Byte Count：`08`
- 實際資料區：`10203040`，每通道 2 位 HEX

2 通道的同類型規格例：

```text
:011000010002041020B8\r\n
```

### 4.4 DPI2／512 段處理

512 段每通道必須使用 4 位 HEX。程式回歸測試例：

```text
CH1 = 0010
CH2 = 0020
CH3 = 0030
CH4 = 0040
```

完整封包：

```text
:01100001000408001000200030004042\r\n
```

### 4.5 裝置正常回應格式

功能碼 10 的正常回應不帶回全部寫入資料，只回傳起始位址與成功處理的暫存器數量：

```text
: + 站號 + 10 + 起始位址(4) + 數量(4) + LRC + CRLF
```

4 通道範例：

```text
:011000010004EA\r\n
```

2 通道範例：

```text
:011000010002EC\r\n
```

目前網頁只有在回應的站號、功能碼、起始位址、數量及 LRC 均與待回應請求相符時，才顯示「10 寫入確認」。

## 五、功能碼 03：多筆連續讀取

### 5.1 PC 發送格式

```text
: + 站號(2) + 03 + 起始位址(4) + 暫存器數量(4) + LRC(2) + CRLF
```

讀取 CH1～CH2 的規格圖範例：

```text
:010300010002F9\r\n
```

### 5.2 裝置回應格式

```text
: + 站號(2) + 03 + Byte Count(2) + 資料 + LRC(2) + CRLF
```

規格圖範例回傳 `0080`、`0030`：

```text
:0103040080003048\r\n
```

欄位拆解：

```text
: | 01 | 03 | 04 | 0080 0030 | 48 | CRLF
```

### 5.3 讀取回應資料寬度

03 回應中的每個暫存器仍依規格圖占 2 Bytes／4 位 HEX：

- 256 段的數值會有前導 `00`，例如 `0080`。
- 512 段可使用至 `01FF`。
- Byte Count 必須等於暫存器數量的兩倍。

因此 256 段的特殊壓縮只出現在功能碼 10 的「發送資料區」，不能誤套到 03 回應解析。

### 5.4 目前網頁回應解析

網頁收到 03 回應後會：

1. 驗證 `:`、HEX 字元、長度及 LRC。
2. 讀取 Byte Count。
3. 確認 Byte Count 為偶數。
4. 確認資料長度等於 Byte Count。
5. 依每 4 位 HEX 拆出一個暫存器值。
6. 找出對應的待回應 03 請求。
7. 使用該請求的起始位址，更新正確的連續通道，而不是固定從 CH1 開始。
8. 驗證每筆回傳值沒有超過目前選擇的解析度。

## 六、起始通道不必固定為 01

「不一定由 01 開始」指的是 **起始暫存器／起始通道**，不是把站號與暫存器位址混為一談。

- 站號：封包前段的 `01`，規格圖範例使用 `01`。
- 起始暫存器：例如 `0001`、`0002`、`0003`，代表從哪一個通道開始。
- Qty：要處理的暫存器筆數，不是結束通道編號。

有效範圍公式：

```text
結束通道 = 起始通道 + Qty - 1
```

必須符合：

```text
1 ≤ 起始通道 ≤ 控制器通道數
Qty ≥ 1
結束通道 ≤ 控制器通道數
```

### 6.1 4CH 控制器範例

| 要操作的通道 | 起始位址 | Qty | 結果 |
|---|---:|---:|---|
| CH1～CH4 | `0001` | `0004` | 有效 |
| CH1～CH2 | `0001` | `0002` | 有效 |
| CH2～CH3 | `0002` | `0002` | 有效 |
| CH2～CH4 | `0002` | `0003` | 有效 |
| 從 CH2、Qty 4 | `0002` | `0004` | 無效，結束會到 CH5 |

### 6.2 8CH 控制器範例

| 要操作的通道 | 起始位址 | Qty | 結果 |
|---|---:|---:|---|
| CH1～CH8 | `0001` | `0008` | 有效 |
| CH2～CH7 | `0002` | `0006` | 有效 |
| CH2～CH8 | `0002` | `0007` | 有效 |
| 從 CH2、Qty 8 | `0002` | `0008` | 無效，結束會到 CH9 |

03 與 10 都使用相同的連續範圍規則。10 不必一次寫入全部通道；03 也不必固定從 CH1 開始讀取。

## 八、介面與標示文字優化紀錄

### 8.1 名稱與版本

- 主標題由「定電流調光器 Web 控制台」精簡為「調光器 Web 控制台」。
- 正式操作版標示為 V1.1。
- 另建立 S1.1 儀器風格實驗版；協定功能與 V1.1 對齊，視覺設計不同。

### 8.2 Serial 區塊

- 「Serial 連接設定」移至控制器通道數量上方，採一橫列排列。
- 「COM Port 未連接／已連接」狀態移入同一區塊。
- Baud Rate 選項保留清楚的 `19200 Baud`、`115200 Baud`，移除容易誤導的產品類型括號文字。

### 8.3 控制器設定

- 控制器通道數量改為 1／2／4／8 可選。
- 解析度標示改為「調光器解析度（請依調光器手冊選擇）」。
- V1.1 的 256／512 選取狀態統一使用藍色，未選取狀態維持灰色。
- 最大數值依解析度同步更新：256 段為 255，512 段為 511。

### 8.4 Modbus 封包發送器

- 標題改為「Modbus ASCII 封包發送器（依協定順序排列）」。
- 封包發送器移至通訊終端外，讓組包與終端顯示成為兩個獨立區域。
- 欄位依協定順序顯示：站號、功能碼、暫存器／起始位址、數值／Qty、Byte Count、多筆資料、LRC。
- 功能碼文字明確標示：
  - `06（單筆寫入）`
  - `03（多筆讀取）`
  - `10（多筆寫入）`
- 03／10 的數量欄補充「Qty（暫存器筆數）」，避免誤認為結束通道。
- 10 依解析度標示：
  - 256 段：2 位 HEX／通道
  - 512 段：4 位 HEX／通道
- 完整 ASCII 封包即時預覽，LRC同步更新。

### 8.5 錯誤訊息

已將模糊錯誤改成可直接判斷原因的文字，例如：

- 「範圍超出：從 CH2 開始最多 7 筆（到 CH8）。Qty 是暫存器筆數，不是結束通道。」
- 「資料長度不符：在 512 段模式下，數量 N 個暫存器應為 N×4 位 HEX。」
- 「資料長度不符：在 256 段模式下，數量 N 個暫存器應為 N×2 位 HEX。」
- 「LRC 錯誤：收到 XX，應為 YY。」
- 「03 回應未套用：找不到對應讀取請求。」
- 「06／10 回應未確認：回應內容與待回應請求不符。」

### 8.6 模擬功能處理

- 原模擬功能只能測試網頁內部組包與解析流程，不能證明設備已寫入。
- 已將模擬回應與實體 COM 回應分開，避免顯示成實機「寫入確認」。
- 按下斷開時會停止模擬計時器並清除模擬待回應資料。
- 因實際測試價值有限，V1.1／S1.1 的模擬器控制入口目前皆已隱藏；底層程式保留，方便還原或後續改造成離線封包測試工具。

## 十一、後續實機測試建議

每一產品至少保留以下測試紀錄：

1. 產品型號與選擇的解析度。
2. 通道數量設定。
3. COM Port與Baud Rate。
4. 實際TX完整封包。
5. 實際RX完整封包。
6. LRC驗證結果。
7. 設備輸出是否真的改變。
8. 讀回值是否與寫入值一致。

建議依序測試：

- 06：CH1、最後一個通道、解析度上限值。
- 10：全部通道、從CH2開始的部分範圍、最後兩個通道。
- 03：全部通道、CH2起始範圍、只讀最後一個通道。
- 錯誤情境：超出通道、超出解析度、錯誤LRC、回應長度不符及斷線。

只有在實體設備回應且輸出行為一致後，才能判定硬體通訊完成驗證。

### 12.13 交給另一個AI時的強制解讀規則

另一個AI依本MD開發時，必須遵守以下優先順序：

1. 以本章逐欄轉錄及黃金封包為協定依據，不用一般Modbus經驗覆寫廠商特殊格式。
